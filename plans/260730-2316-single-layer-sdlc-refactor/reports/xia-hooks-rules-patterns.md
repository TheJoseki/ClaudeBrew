# ClaudeKit-Engineer Hooks + Rules Patterns — for ClaudeBrew Single-Layer Refactor

Source: `C:/Works/Tool/ClaudeKit.CC/claudekit-engineer/claude/` (read-only). Contrast: `C:/Works/Tool/AWSClaw/ClaudeBrew/plugins/cbr/hooks/hooks.json`.

## 1. Hook architecture

- **Registry = `claude/settings.json` `hooks{}`.** Standard Claude Code event map: `SessionStart`, `UserPromptSubmit`, `SubagentStart`, `PreToolUse`, `PostToolUse`, `SubagentStop`, `Stop`. (`claude/hooks/managed-hooks.json:1-16` is a *derived* list the CLI self-heal reads to detect drift — generated from settings.json, not authoritative itself.)
- **Matcher style — general, not agent-typed.** `SubagentStart`/`SubagentStop` in `settings.json:51-59,109-127` have **no matcher at all** (fire for every subagent) or match on `Plan` (the built-in plan-mode subagent type), never on a custom `.*-agent` name string. `PreToolUse`/`PostToolUse` match on **tool names** (`Write`, `Bash|Glob|Grep|Read|Edit|Write`, `Edit|Write|MultiEdit`, `Task|TaskCreate|TaskUpdate|TodoWrite`). ClaudeBrew's current `hooks.json` is the outlier — its `.*-agent` matcher assumes named role-agent files, which ClaudeKit's flat single-layer skill design never needed.
- **Registry pattern: `<hook>.cjs` (thin CLI entry) + `lib/*.cjs` (pure logic, shared/testable) + JSON config.** Every hook file follows: crash-wrapped `try{}` at top level → `isHookEnabled('<name>')` early-exit from `lib/ck-config-utils.cjs` config (`hooks.<name>: true|false` in `.claude/.ck.json`, defaults in `ck-config-utils.cjs:70-81`) → read stdin JSON → delegate to `lib/` for logic → format output → `logHookCrash` on any error, **always exit 0 on crash (fail-open)**. The `lib/` split exists explicitly "for OpenCode plugin reuse" (comments in `session-init.cjs:11`, `scout-block.cjs:24`, `dev-rules-reminder.cjs:11`) — i.e., decouple Claude-Code-specific I/O from portable business logic.
- **stdin/exit-code contract:** hooks read the full tool/event payload as JSON from stdin (`fs.readFileSync(0,'utf-8')`). Exit `0` = allow/continue (even on internal error — fail-open is universal here, no hook exits nonzero on its own crash). Exit `2` = **block**, paired with either a plain stderr message (`PreToolUse` blocks, e.g. `scout-block.cjs:124,144`, `privacy-block.cjs:156`) or a JSON `{continue:false, decision:'block', reason}` on stdout (`UserPromptSubmit` blocks, e.g. `simplify-gate.cjs:183-185`, `workflow-artifact-gate.cjs:61-62,104-105`). Non-blocking context injection uses `{hookSpecificOutput:{hookEventName, additionalContext}}` (e.g. `subagent-init.cjs:207-212`, `descriptive-name.cjs:23-29`, `plan-format-kanban.cjs:90`).

## 2. What hooks ENFORCE

| Hook | Event / matcher | Enforces |
|---|---|---|
| `scout-block.cjs` | `PreToolUse`, tool=`Bash\|Glob\|Grep\|Read\|Edit\|Write` | Blocks (exit 2) reads/edits into heavy dirs (`node_modules`, `.git`, `dist`…) via gitignore-spec `.ckignore`; allows recognized build commands. Pure filesystem-noise gate, not workflow. |
| `privacy-block.cjs` | `PreToolUse`, same matcher | Blocks (exit 2) reading sensitive files (`.env`, keys) unless prefixed `APPROVED:`; emits a JSON marker instructing Claude to run `AskUserQuestion` first. **Human-gate-via-prompt-protocol pattern**, not a hard deny — the block is really "ask before proceeding," enforced deterministically at the tool layer. |
| `descriptive-name.cjs` | `PreToolUse`, tool=`Write` | Soft — injects naming-convention reminder before every Write; never blocks. |
| `simplify-gate.cjs` | `UserPromptSubmit` (general, no tool matcher) | **Hard-blocks** (exit 2) ship/merge/pr/deploy/publish verbs when `git diff HEAD` shows an unsimplified diff (LOC/file-count/single-file thresholds computed live, stateless); **soft-warns** commit/finalize/release. Config-gated (`gate.enabled` default `false`). This is the cleanest example of a **deterministic quality gate with zero agent/subagent involvement** — pure git-state + regex-on-prompt. |
| `workflow-artifact-gate.cjs` + `workflow-artifact-gate/*.cjs` | Not wired in shipped `settings.json` at all (default `hooks['workflow-artifact-gate']=false`); ships as **manual CLI** invoked by skill instructions, optionally wireable to `UserPromptSubmit` or `PreToolUse:Bash` (docs `hooks/docs/README.md:158-215`) | **The artifact gate** — see below. |
| `dev-rules-reminder.cjs` | `UserPromptSubmit` (general) | Non-blocking — injects rules/plan-context summary once per scope (dedup via `context-builder.cjs` reservation logic), not an enforcement gate. |
| `cook-after-plan-reminder.cjs` | `SubagentStop`, matcher=`Plan` | Non-blocking — after the built-in Plan subagent stops, prints "ask user for next step" + `/ck:cook <path>` hint. This is the closest ClaudeKit analog to a stage-transition nudge, and it deliberately does **not** auto-cascade. |
| `plan-format-kanban.cjs` | `PostToolUse`, matcher=`Edit\|Write\|MultiEdit` | Warns (never blocks) on `plan.md` formatting drift (filename-as-link-text, direct status-table edits bypassing the `ck plan` CLI). |

### How `workflow-artifact-gate` enforces workflow **without agents**

This is the direct analog for ClaudeBrew's Decision 1 ("verdict + user gate"). Mechanism, end to end:

1. **Skills instruct Claude to *write* JSON artifacts** to a known directory (`plans/<plan>/reports/harness/` or `plans/reports/harness/<slug>/`), documented once in the shared reference `claude/skills/_shared/references/workflow-artifacts.md` and consumed by `cook`/`fix`'s `review-cycle.md`. Five files: `context-snippets.json`, `risk-gate.json`, `verification.json`, `review-decision.json`, `adversarial-validation.json` (the last conditionally required for auto/high-risk/ship-like stages).
2. **A tiny pointer file** `.claude/workflow-artifacts.json` records which dir is "active" (metadata only — no secrets), read by `workflow-artifact-gate/artifact-locator.cjs:58-83` with a 3-tier fallback: explicit `--artifact-dir` flag → `CK_WORKFLOW_ARTIFACT_DIR` env → pointer file → single-candidate directory scan (24h recency window).
3. **Claude itself runs the validator as a Bash command** (`node claude/hooks/workflow-artifact-gate.cjs --stage finalize --artifact-dir <dir>`) — this is the crux: no hook auto-fires; the *skill's own instructions* (`review-cycle.md:22-26`) tell Claude to invoke the CLI deterministically before finalize/commit/ship/push/PR/deploy. The validator (`workflow-artifact-gate/validator.cjs`) checks schema shape, secret-pattern leakage (regex bank for API keys/bearer tokens/AWS keys/PEM blocks, `validator.cjs:21-29`), and **policy**: hard stages (`ship|push|pr|deploy`) require all 5 artifacts + `review-decision.decision === 'PASS'` + at least one passing verification command + no disproven/unverified adversarial claims; high-risk `--auto` mode requires `risk-gate.humanApproved === true` before proceeding. Exit code 2 = block.
4. **The human gate is layered on top via `AskUserQuestion`**, not the hook — `review-cycle.md:44-64` (interactive) and `:66-91` (auto) both route "validator blocks OR critical issue" and "high-risk auto-stop" straight to `AskUserQuestion`, capped at 3 fix-cycles before forcing a final user decision. The **hook only makes "PASS" deterministic and unfakeable** (schema + secret-scan + policy checks on structured evidence); the **stop-and-ask is a skill-level instruction**, matching ClaudeBrew's "verdict + user" model exactly.
5. **Because it's invoked by skill instruction rather than an automatic hook, it needs no `.*-agent` (or any) matcher** — it works identically whether the writer of the artifacts was the main thread, a `general-purpose` subagent, or a human-edited file. This is the load-bearing insight for ClaudeBrew: **enforcement lives in what the skill tells Claude to run + what artifact schema it demands, not in which subagent type produced the work.**

## 3. Rules structure

6 files, `claude/rules/*.md`, **215 total lines** (`CLAUDE.md` 43, `development-rules` 27, `documentation-management` 40, `orchestration-protocol` 42, `primary-workflow` 29, `review-audit-self-decision` 34):

- **`CLAUDE.md` is the only always-loaded file** (it's literally the project's root context file). It stays deliberately thin — 6 bullet "Core Rules" + a **pointer table** to the other 5 ("On-Demand References") + a second pointer table to skill-owned routing docs (`find-skills/references/domain-routing.md`, etc.) + hook-response protocol (privacy-block JSON marker) + skill-venv note. It explicitly says: *"Keep it short. Load the linked rule files only when the current task needs them."*
- **The other 5 are on-demand, loaded by filename-matching intent**, not injected by any hook: `development-rules.md` (implementation/verification baseline — YAGNI/KISS/DRY, no fake data, quality gates, commit hygiene), `primary-workflow.md` (Understand→Implement→Verify→Review workflow shape), `orchestration-protocol.md` (delegation context, context isolation, parallel-work rules, status protocol, **model-escalation-to-`kongming`-advisor** pattern), `documentation-management.md` (when to update docs, plan location `plans/<slug>/`), `review-audit-self-decision.md` (verified-decision permanence, user-decision protection, threat-model-before-fix, scout-first).
- **Boundary: rules vs. skills.** Rules hold cross-cutting, stage-agnostic *policy* (how to behave regardless of task). Skills hold stage-specific *procedure* (what steps to run for this task type) plus their own routing references. `CLAUDE.md` never duplicates skill content — it points at it. This mirrors what ClaudeBrew's `brainstorming`/`worktree` reference-file split already does (`SKILL.md` thin + `references/*.md` deep) — ClaudeKit does the same split one level up, at the rules layer.
- **Why only 6:** every rule answers "what should Claude do differently regardless of which skill is active" — logging none of this per-skill avoids the 16-rules sprawl ClaudeBrew inherited (10 of which were almost certainly orchestration/agent-role plumbing specific to the two-layer engine being removed).

## 4. Apply to ClaudeBrew plan

1. **Adopt `simplify-gate.cjs`'s pattern directly as the model for Decision 1's replacement enforcement**, not a literal port: a general `UserPromptSubmit` (or `PreToolUse:Bash`) hook that computes live git-diff signals and hard-blocks ship-like verbs, config-gated and fail-open. Ties to **Phase 1** (hooks.json rework) — gives ClaudeBrew a deterministic backstop that fires regardless of which skill or subagent produced the diff, replacing the deleted `.*-agent` `SubagentStop` quality-gate without needing agent typing.
2. **Do not port `workflow-artifact-gate.cjs` wholesale — port its *shape*.** ClaudeBrew's Decision 1 already chose "verdict + user gate" (skill writes PASS/FAIL + findings into its own artifact, stops, human decides). The ClaudeKit artifact-gate shows the natural next increment *if* ClaudeBrew ever wants machine-checkable hard gates later: define one shared artifact schema (in a `_shared`-style reference, matching `sdlc-conventions.md`'s existing artifact-path table) + one standalone validator script invoked **by skill instruction via Bash**, never by an automatic agent-matcher hook. Relevant to **Phase 3** (gate/artifact table rewrite) as a documented "future option," not required scope now.
3. **Trim rules toward the 6-file/CLAUDE.md-hub model in Phase 1/Phase 3.** Concretely: keep one always-loaded root file (ClaudeBrew's own `CLAUDE.md`) as a thin hub with an "On-Demand References" pointer table; fold orchestration-only content out of `orchestration-protocol.md`-equivalent once the agent layer is gone (ClaudeKit's version already excludes agent-role plumbing — it only covers subagent/team delegation *context*, which ClaudeBrew still needs for its `--parallel` `general-purpose`-subagent mode per Decision 2). Target ~12 rules per the plan's "Net effect" line is consistent with this — don't over-trim to exactly 6; ClaudeBrew's SDLC domain (gates G1–G8, artifact paths) legitimately needs more policy surface than a generalist toolkit.
4. **Reuse the `lib/`-split pattern for any new general hooks** written in Phase 1: put the actual git-diff/threshold/schema logic in a plain, dependency-free `lib/*.cjs` (or `.py`, matching ClaudeBrew's existing Python hook convention) module with no Claude-Code-specific I/O, and keep the hook entrypoint a thin stdin→lib→stdout/exit wrapper. This is what makes ClaudeKit's hooks unit-testable (`hooks/__tests__/*.test.cjs` mirror every `lib/*.cjs`) — ClaudeBrew's `evals/test_hook.py` for `enforce-worktree.py` is already this shape; extend the convention to any replacement gate hook rather than inlining logic in the hook file.
5. **Keep matchers general (tool-name or none), never reintroduce a `.*-agent`-style string matcher** — ClaudeKit has zero examples of matching on a custom agent-name pattern; every SubagentStart/Stop hook either matches nothing (fires for all) or matches the built-in `Plan` type. This directly validates removing `subagent-context-inject.js`/`subagent-quality-gate.py` and their `.*-agent` matcher entries in Phase 1 — there's no ClaudeKit precedent to preserve that shape, so nothing is lost by deleting it outright.
6. **`cook-after-plan-reminder.cjs` (SubagentStop, matcher=`Plan`) is a low-cost, high-value pattern worth adding** in Phase 1/2: a stage-transition nudge that prints "ask the user which next step" + the exact next-skill invocation string, fired off the *built-in* Plan-mode stop event — no custom agent needed. Could be adapted for ClaudeBrew's own stage skills (e.g., after `implement-feature` stops, remind the user of `unit-test`/`review-code` invocation strings) while still respecting the hard "no auto-cascade" house rule, since the hook only prints a suggestion, never invokes anything.
7. **`descriptive-name.cjs` and `plan-format-kanban.cjs` are cheap wins with no dependency on the agent layer** — pure `PreToolUse:Write` / `PostToolUse:Edit|Write|MultiEdit` reminders. Low priority (Phase 3, polish) but trivial to port if ClaudeBrew wants consistent artifact/report naming enforcement across skills without agent involvement.
8. **`privacy-block.cjs`'s "block + JSON marker for `AskUserQuestion`" protocol** is a reusable pattern for any future ClaudeBrew hook that needs a human decision gate without an LLM judgment call embedded in the hook itself: the hook only detects the *condition*; the *decision protocol* (ask, then retry with an approval token) lives in the paired rule (`CLAUDE.md`'s "Hook Responses" section, `rules/CLAUDE.md:32-34`). Consider documenting an equivalent "Hook Responses" contract in ClaudeBrew's trimmed root rule file rather than embedding the AskUserQuestion protocol only in the hook's stderr text.
